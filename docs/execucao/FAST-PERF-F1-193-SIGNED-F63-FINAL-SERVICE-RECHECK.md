# FAST-PERF F1-193 — bloqueio final de cancelamento entre entrega assinada e renderização HTML

**Base F192/PR #300, CI PostgreSQL16 descartável, DRAFT/NO-GO.**

F192 exigiu serviço sintético elegível, geração estável e assinatura real de bytes Ed25519 do emissor histórico original do Portal durante a entrega JSON F180. F181, porém, ainda tratava o recibo F180 apenas como arquivo com SHA256 e gerava a prévia HTML F63 original sem consultar novamente o PostgreSQL. Isso permitia construir um HTML de demonstração com dados anteriormente válidos **depois** de uma revogação de serviço, mesmo que o arquivo JSON não tivesse sido adulterado.

F193 amplia **os componentes existentes** sem novo protocolo: F192 agora acrescenta ao resultado **na mesma memória de processo** as duas gerações locais `service_epoch_at_delivery` (empresa e serviço) apenas quando o serviço sintético foi validado. A classe original `SyntheticF181BoundPortalHtml` ganha um **parâmetro PDO opcional** e, sob flag de CI `PERF_F193_F63_SERVICE_LAB=1`, exige a ligação entre nonce F124 já consumido, arquivo original F100 com SHA correto, conexão PostgreSQL autenticada F91, geração F191 idêntica à do fim de F192 e **nova consulta F189/F100 idêntica ao JSON**. As checagens ocorrem antes da janela de teste concorrente, após essa janela e **depois de executar o próprio renderer F63**, antes de persistir HTML. A falta de conexão, qualquer divergência de dados, versão ou serviço bloqueia o documento final sem criar arquivo.

O teste usa **quatro novas assinaturas** geradas pelo emissor PHP original histórico do Portal (chaves efêmeras apenas no CI). Demonstra: (1) sucesso com serviço de demonstração e página real F63 byte a byte idêntica à prévia F192; (2) cancelamento do vínculo **após o recibo F192 e antes do F63**, sem HTML, inclusive depois de reativação porque epoch mudou; (3) mudança `active→pending→active` injetada entre duas verificações F181, detectada mesmo com DTO F100 igual; (4) arquivo F100 modificado para uma conta inventada **junto com o hash fornecido pelo chamador**: a validação falha pela comparação com uma nova leitura SQL, não por um checksum simples. Restabelecer o documento original volta a permitir apenas uma prévia offline, sem reutilizar o nonce assinado para nova entrega. Teste também comprova que F63 não consome nonces.

**Limitações:** o HTML é estático, sem autorização HTTP em tempo real; depois da última checagem uma revogação pode ocorrer e o arquivo temporário já existente ainda pode ser aberto. Um atacante privilegiado que controle o banco SQL, seu backup e o processo PHP pode forjar provas locais; essa geração não é WORM, fonte externa confiável nem login de cliente. O emissor histórico F29 e a fonte de elegibilidade continuam sintéticos; F62/F63 não se transformam em painel operacional. Before production: independent Portal IAM/contract authority, leases/revocation, AppSec/DBA review, external antirollback and authorized UI architecture.
